# 資料儲存與復原（H2.1）

## 位置與格式
- 資料夾：`private/allay-hub/`（在 private/ 底下，不會上傳）。
  - `hub.json`：綁定碼（只存雜湊）、linkId → 悅靈的查詢表、鎖定狀態。**不放任何授權**。
  - `pets/<petId>.json`：每隻悅靈一份。狀態、epoch、控制者、去重紀錄、記憶、對話、冒險紀錄、意圖、**授權（links）與待確認的綁定（pendingLinks）**都在同一份。
  - `quarantine/`：啟動時保留的診斷證據（沒 ACK 的暫存檔、損壞檔案的複本、人工復原紀錄）。
- 每份檔案的外層：`{ format: "fairy-hub-doc", hubSchema: 1, sha256, body }`。`sha256` 是 body 以固定順序序列化後的雜湊。

## 交易（一次寫入）
1. 在記憶體的複本上算出新的文件（失敗就整個丟掉）。
2. 寫入 `<name>.tmp.json` 並 fsync。
3. 把目前的正式檔複製成 `<name>.prev.json`（只當診斷證據，**不會自動拿來復原**）。
4. 把暫存檔改名成正式檔（NTFS 上是原子的）。
5. **成功後**才更新記憶體快取、回傳 ACK。

任何一步失敗都回 `503 STORE_UNAVAILABLE`：記憶體快取不變、正式檔不變，不會有部分寫入。
一個請求從讀取到寫入之間沒有 `await`（聊天在 AI 回答後會重新讀取、重新驗證），同一份文件的寫入不會交錯。

## 跨文件的操作（H2.1）
| 操作 | 寫入 | 失敗時 |
|---|---|---|
| 綁定確認、拒絕、撤銷 | **只寫悅靈文件**（單一交易） | 什麼都沒生效（或維持原狀），明確回 503，可以重試 |
| 綁定碼使用（claim） | ① hub.json：作廢綁定碼、記下 linkId → ② 悅靈文件：記下待確認 | ①失敗：碼還能用、沒有待確認；②失敗：碼已作廢、沒有待確認、狀態 `failed`。**兩種都不會產生授權** |
| 產生綁定碼 | 只寫 hub.json | 沒有碼 |

hub.json 損壞時：所有綁定相關操作回 503；已確認的授權在悅靈文件裡，不受影響。

## 啟動時的復原（fail-closed）
| 情況 | 判斷 | 處理 | 測試 |
|---|---|---|---|
| 正式檔正確 | 正常 | 使用；殘留的暫存檔（沒 ACK 的寫入）移到 quarantine/ | 「當機在暫存檔寫好、還沒換上」 |
| 只有暫存檔（沒有正式檔、也沒有前一版） | **第一次建立就中斷**，從未 ACK | 暫存檔移到 quarantine/，當作不存在 | 「P1-5 第一次建立就中斷」 |
| 正式檔損壞（檢查碼或格式不對） | **資料損壞** | 不自動退回前一版；整份標記無法使用（請求回 503、拒絕覆寫、拒絕重新登記）；正式檔、暫存檔、前一版都複製到 quarantine/；原檔留在原地，重啟後仍是損壞狀態 | 「P1-5 正式檔損壞」、「P1-5 撤銷後正式檔損壞」 |
| 正式檔不見但有前一版 | **資料損壞**（不是首次建立） | 同上 | 「P1-5 正式檔不見但有前一版」 |

為什麼不自動退回前一版：前一版可能還是「綁定 active」、epoch 比較舊、或少了已 ACK 的事件。自動退回會讓撤銷過的權限重新開放、讓事件或 epoch 靜默回退。

**人工復原**（管理者的決定，服務必須先停止）：
```
node scripts/hub/backup-cli.mjs recover <名稱> prev|tmp [--pets]
```
會先把目前的檔案複製到 `quarantine/<名稱>-manual-<時間>/`，寫下 `RECOVERY.txt`（用哪一份、rev、epoch），再換上指定的版本。

轉接服務啟動時會印出：載入幾隻、無法載入（資料損壞）幾隻、中斷的第一次建立幾隻。

## 去重的耐久性
- 去重紀錄（角色＋來源 ID＋opId → 內容雜湊、當時的 rev 與結果）和狀態在**同一份檔案、同一次交易**寫入。
- 已 ACK 的事件在重啟後重送：回 `DUPLICATE` 與當初的結果。
- 沒 ACK 的事件（例如儲存失敗）重送：會正常套用一次。
- 保留 30 天；每隻上限 20,000 筆，滿了回 `507 CAPACITY_REJECTED`，不會刪掉未過期的紀錄。
- 超過 30 天被清掉的紀錄如果被重送：`baseRevision` 早已過時，會被 `REVISION_CONFLICT` 擋下。

## 備份（H2.1）
```
node scripts/hub/backup-cli.mjs backup <放快照的資料夾>      ← 服務停止時
node scripts/hub/backup-cli.mjs verify <快照>
```
- 拒絕：來源資料夾不存在（`BACKUP_SOURCE_MISSING`）、意外的空資料（`BACKUP_EMPTY`，要明確允許才可以）、損壞的文件（`BACKUP_SOURCE_CORRUPT`）、跨文件不一致（`BACKUP_INVALID`）。
- 跨文件一致性：悅靈文件的 `pet` 與檔名相同、有整數的 rev／epoch；綁定碼與 linkId 指向存在的悅靈；有悅靈文件時必須有 hub.json。
- **一致的視圖**：CLI 把整組檔案讀兩次，內容完全相同才採用（最多 3 次，否則 `BACKUP_UNSTABLE`）。執行中的 Hub 可以用 `hub.backup(資料夾)` 從記憶體快取同步建立快照（同一個時間點，不會讀到寫一半的資料）。
- 清單 `manifest.json`：每個檔案的 SHA-256、悅靈數量、是否明確允許空資料。

## 還原（H2.1）
```
node scripts/hub/backup-cli.mjs restore <快照> [--allow-rollback]    ← 先停止轉接服務
```
1. 完整驗證：清單、每個檔案的雜湊與檢查碼、清單外多出來的檔案、跨文件一致性、悅靈數量。
2. **拒絕回退**：目前資料裡任何一隻悅靈的 rev 或 epoch 比快照新、或快照裡沒有這隻 → `409 ROLLBACK_REFUSED`。確定要回到舊資料時才加 `--allow-rollback`。（目前已損壞的文件不比較，因為還原正是要處理它。）
3. 寫到暫存資料夾；**中途失敗**就刪掉暫存資料夾，原資料完全不動。
4. 原資料夾改名為 `allay-hub.old-<時間>` → 暫存資料夾改名成正式；**第二步失敗**就把原資料夾改回原位。

| 測試 | 內容 |
|---|---|
| P1-6 備份：來源不存在、空資料、損壞的來源、跨文件不一致都拒絕 | |
| P1-6 備份：資料在備份期間一直變動 → BACKUP_UNSTABLE | 一致的視圖 |
| P1-6 驗證：少檔、多檔、清單空白、雜湊不符都拒絕 | 不完整的快照 |
| P1-6 還原：拒絕回退（明確允許才放行） | |
| P1-6 還原中途失敗：複製失敗、替換失敗 | 原資料都不受影響 |
| P1-6 執行中的 Hub 快照 | 從快取建立、還原後狀態相同 |

## 尚未涵蓋
- 多個程序同時寫入（目前只有一個轉接服務）。
- 磁碟本身故障（需要放到另一顆硬碟的定期備份；另批處理）。
- 還原或人工復原時轉接服務還在執行：記憶體裡的資料會蓋回去。**必須先停止轉接服務**（目前靠操作流程，程式沒有強制檢查）。
