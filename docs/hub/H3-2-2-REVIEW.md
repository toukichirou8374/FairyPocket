## 修補（`scripts/hub/localai.mjs`）
| 入口 | 修補 |
|---|---|
| `getJson()`（`/api/tags`） | 收到回應時**先檢查 `statusCode === 200`**；不是 200 → 讀掉內容（`r.resume()` 釋放連線）並丟出錯誤，**不解析 JSON**。`verify()` 視為驗證失敗（原因沿用 `unreachable`，狀態碼放在 `lastCheck.detail`，例如 `http_500`），`ask()` 在 `http.request('/api/chat')` 之前就丟出錯誤 → 不送聊天推論 |
| `ask()` 的 `/api/chat` 回應 | **先檢查 `statusCode === 200`**，之後才做 H3-2.1 的 model 身分、remote 欄位、內容型別檢查；不是 200 → 讀掉內容並拒絕 → 排程器改用規則台詞，回答不被接受、不保存 |

- 只接受 200（Ollama 正常回應就是 200）；201、204、3xx、4xx、5xx 都拒絕。
- 沒有改變：每次推論前重新驗證、固定 digest、雲端模型拒絕、回應模型身分核對、逾時、取消（AbortSignal）、名額等底層結束才釋放、規則降級、音效契約。
- 原因代碼沿用 `unreachable` 是為了不改動既有測試（H3-2.1 的測試對 500 斷言 `unreachable`）。
- `/api/chat` 的狀態碼是回應後才知道：這種情況**推論已送出**，修補保證的是回答不被接受、不輸出、不保存。

## 文件更正（`H3-2-REPORT.md`）
- **160 tokens**：只是上限（`num_predict`），不是預期長度；不能用它推算「自然結束的時間」，也不能證明推論因為取消而更早停止。
- **GPU 時間戳**：同步取樣讓 GPU 樣本成批延遲，所以時間線不能判斷先後順序或停止時間，連「約 1.2 秒內回到基準」也不能當成精確結論。能確定的只有測試結束後 3 秒內 CPU 增加 0 ms、GPU 回到 16%。
- 取消的結論維持「與停止推論一致，但不是證明；GPU 停止運算尚無直接證明」。
- `CONTRACT.md` 補上兩個 HTTP 入口都必須是 200 的規則。

## 建議複審重點
1. 兩個入口的狀態碼檢查都在解析 JSON 之前；非 200 時有 `r.resume()`，不會留下未讀的回應。
2. `/api/tags` 失敗時，`ask()` 在送出 `/api/chat` 之前就結束。
3. 排程器的錯誤處理沒有變：錯誤 → `RULES`（reason `error`）。
